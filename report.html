대회 이미지에서 글자와 그림 설명을 뽑아본 과정

왜 조사했는지, 무엇을 연결해 실행했는지, 실제로 무엇이 나왔는지 · 2026.09.26

조사·실험 진행 정리논문 조사 노트43개 예시 모아보기299개 원문·좌표 확인재실행·기록시작코드 설명데이터 안내GitHub

이번에 한 일부터 간단히 설명하면

대회 이미지에는 사진만 있는 것도 있고, 한글 안내문이나 로고처럼 글자를 읽어야 내용을 알 수 있는 이미지도 있었다. 그래서 이미지를 설명하는 모델 하나만으로 필요한 정보를 다 얻을 수 있는지부터 확인하고자 하였다.

이를 위해 관련 논문을 찾아보고, 공개된 모델 중 그림을 설명하는 모델 2개와 글자를 읽는 OCR 도구 2개를 골라 로컬 샘플에 실행하였다. 작은 글자는 확대하고, 긴 포스터는 나눠 읽어 보는 처리도 추가하였다.

돌려 보니 글자는 OCR에서 더 직접적으로 얻을 수 있었고, 그림 설명 모델은 장면을 알려주면서도 없는 내용을 덧붙이는 경우가 있었다. 현재까지 만든 것은 이미지에서 정보를 뽑아 비교·저장하는 실험 도구이다. 이 결과를 Gemma에 넣어 최종 판정하는 단계는 아직 진행하지 않았다.

이 자료는 아래 순서로 읽으면 된다

순서팀원이 이해하면 되는 내용이동
1왜 이미지 설명만으로 충분한지 의심했는가출발점
2어떤 논문을 찾았고, 왜 이 네 모델을 골랐는가자료 조사와 모델 선택

1. 시작은 “사진 설명 모델로 한글 안내문도 설명할 수 있을까?”였다

기존에 검토하던 Patch-ioner는 이미지의 전체 또는 일부 영역을 문장으로 설명하는 방법이다. 그런데 우리 샘플에는 기관 로고, 날짜가 적힌 행사 포스터, 숫자와 창구명이 들어간 배치도도 있었다. 이런 이미지에서는 “사람이 있다”, “표지판처럼 보인다”는 설명만 얻어서는 중요한 정보가 빠진다.

예를 들어 국민연금 홍보 이미지에서 가족 사진을 잘 설명하더라도, “국민연금”이라는 글자를 놓치면 무슨 안내인지 알기 어렵다. 반대로 글자만 읽으면 사진 속 대상이나 도형의 의미가 빠질 수 있다. 따라서 다음 두 작업을 나누어 조사하였다.

  • 그림·사진 설명: 무엇이 있고, 어떤 장면이며, 대상이 어떻게 배치되어 있는지 추출한다. 이를 이미지 캡셔닝이라고 한다.
  • 글자 읽기: 이미지 속 글자의 위치를 찾고, 실제 문자열로 바꾼다. 이 작업이 OCR이다. 글자 위치만 찾는 text detection과 구분하였다.

우리의 최종 목적은 기존 alt가 적절한지 판단할 근거를 마련하는 것이다. 이번에는 그 앞단인 이미지 정보 추출 방법을 시험하였다. 최종 대회 과제와 분류 형식은 공식 문제 설명에서 확인하였다.

2. 논문을 조사한 뒤, 비교할 모델 네 개를 골랐다

2-1. 논문 이름보다 “우리 이미지에 실제로 쓸 수 있는가”를 확인하였다

조사는 그림 설명, OCR·문서 읽기, 설명 오류를 줄이는 방법으로 나누어 진행하였다. 2026년 후보 20개를 비교하면서 논문의 방법을 읽고, 공식 GitHub와 모델 배포 페이지를 찾아 실제 실행 가능한 상태인지 확인하였다.

  • 논문에서 확인한 것: 이미지 한 장을 넣으면 무엇이 나오는지, 어떤 비전 처리를 추가하는지 확인하였다.
  • 코드에서 확인한 것: 저장소에 소개글만 있는지, 실행 코드와 모델 파일까지 있는지 확인하였다.
  • 한국어에서 확인한 것: 한국어로 답할 수 있다는 설명과, 이미지 속 한글을 읽는 근거를 구분하였다.
  • 학습 조건: 이번에는 이미 공개된 모델을 사용하고, 대회 데이터로 추가 학습하지 않는 방식으로 한정하였다.

조사해 보니, 아이디어는 적합해도 실행 코드가 없는 방법이 있었고, 글자는 읽지만 사진의 의미까지 설명하지는 않는 방법도 있었다. 지정한 모든 조건을 동시에 확인한 완성형 방법은 이번 후보군에서 찾지 못하였다. 그래서 역할을 나누어 실제로 돌려 볼 수 있는 구성을 먼저 만들었다.

2-2. 네 모델은 각각 이런 일을 맡았다

모델쉽게 말하면이번에 넣은 이유
Patch-ioner이미지 전체나 선택한 부분을 한 문장으로 설명하는 모델이다.기존에 검토한 방법이므로, 우리 이미지에서도 설명이 잘 나오는지 확인하였다.
Florence-2-baseMicrosoft의 이미지 이해 모델이다. 그림·사진을 자세히 설명하고 영역별 설명도 뽑을 수 있다.Patch-ioner와 다른 설명 모델을 함께 써서 장면·도형 설명이 달라지는지 비교하였다.
PP-OCRv5 한국어이미지에 실제로 쓰인 한글을 문자열로 읽는 OCR 모델이다.기관명·날짜·전화번호처럼 caption만으로 놓칠 수 있는 정보를 읽게 하였다.
EasyOCR한국어·영어를 읽을 수 있는 별도의 OCR 도구이다.한 OCR의 출력을 그대로 믿지 않고, 다른 도구와 읽은 결과를 비교하였다.

Florence와 EasyOCR는 2026년 논문 조건을 충족한 최종 선정작이라는 뜻으로 넣지 않았다. 실제 비교 실험을 위한 기존 도구로 사용하였다. 논문 선별 기준과, 실험에 쓸 비교 도구의 선택을 분리한 것이다.

학회 기준도 따로 대조하였다. 사용자가 지정한 BK21 표에서는 CVPR의 발표 유형별 값이 달랐으므로, CVPR이라는 이름만으로 기준을 통과시킨 것은 아니다. 후보별 근거는 아래 표와 별도 조사 노트에 남겼다.

3. 샘플을 열어 보니, 같은 방식으로 넣기 어려운 이미지가 섞여 있었다

실험에는 로컬에 저장된 대회 샘플 299개를 사용하였다. 큰 사진부터 16×16 숫자, 배경이 투명한 아이콘, 글자가 많은 포스터까지 크기와 형태가 달랐다. 먼저 파일을 제대로 열 수 있는지 확인한 뒤 모델에 넣는 과정을 만들었다.

3-1. 압축 파일에서 실제 이미지와 메타데이터를 확인하였다

  • 입력은 로컬 koaltq_sample_299.zip이었다. 299개 레코드와 299개 이미지 파일의 대응을 확인하였다.
  • 파일 내용을 구분하는 값인 SHA-256으로 비교하니, 서로 다른 이미지 내용은 289개였다. 299개 파일 안에 같은 내용의 중복이 있었다.
  • JPEG 157개, PNG 135개, GIF 6개, SVG 1개로 확인하였다. GIF 6개는 모두 한 프레임이었다.
  • 긴 변이 64픽셀 이하인 이미지가 38개였다. 큰 예로 4,961×7,016 포스터와 7,257×4,082 썸네일이 있었다.
  • 확장자가 .do·.es이거나 없어도 이미지 헤더로 포맷을 확인하였다.
  • 비전 모델에는 픽셀만 넣었다. 기존 alt, 페이지 문맥, 정답 label은 입력하지 않았다.

3-2. 모델이 이미지를 제대로 볼 수 있도록 준비하였다

여기서 전처리는 새로운 정보를 만들어 내는 일이 아니다. 이미지의 방향을 맞추고, 투명한 부분에 배경을 넣고, 지원하지 않는 파일을 읽을 수 있게 변환하는 준비 작업이다. 어떤 처리를 했는지 추적할 수 있도록 원본 파일과 결과를 구분해 저장하였다.

단계실제로 한 처리남긴 기록
파일 확인이미지 크기·포맷·프레임·hash를 확인하였다.파일별 목록을 저장하였다.
방향·투명도EXIF 방향을 적용하고, 기본 입력은 흰 배경에 합성하였다.원본과 입력 정책을 구분하였다.
SVG 처리직접 열기 실패 후 resvg로 변환하고 재실행하였다.초기 실패와 보완 결과를 함께 남겼다.
모델 실행각 모델의 자체 resize와 설정으로 추론하였다.문장·OCR 원문·좌표·score·시간을 저장하였다.
추가 관찰작은 입력은 확대하고, 밝은 투명 전경은 대비 배경을 사용하였다. 큰 입력은 타일을 추가하였다.원본 좌표로 복원하고 처리 출처를 남겼다.
비교기본 출력과 보완 출력을 대조하였다.기본 결과를 보완 결과로 덮어쓰지 않았다.

3-3. 잘 안 읽히는 입력에는 세 가지 보완을 시험하였다

글자를 못 읽었다고 모두 같은 원인은 아니었다. 너무 작은 글자는 확대하고, 밝은 투명 글자는 배경을 어둡게 바꾸고, 큰 포스터는 작은 구역으로 나눠 읽어 보았다. 아래 예시는 실제 실험에서 확인한 차이다.

예시 A. 16×16 숫자는 확대 후 읽혔다

  • 긴 변 512를 목표로 하되 최대 8배까지만 확대하였다. 따라서 이 입력은 512가 아니라 128픽셀이 되었다.
  • 오른쪽 이미지는 확대 크기 설명을 위한 브라우저 표시이다. 실제 추론 입력 확대에는 Lanczos를 사용하였다.
  • 작은 이미지를 확대해도 원본에 없는 글자 정보가 새로 생기지는 않는다.

예시 B. 흰 SVG는 배경을 바꾸어 다시 확인하였다

  • 투명도와 전경 밝기로 배경 전환 여부를 결정하였다.
  • 밝은 투명 전경은 흰 배경에서 사라질 수 있음을 확인하였다.
  • 어두운 배경은 OCR용 보완 조건이다. 실제 웹사이트 배경색을 확인한 것은 아니다.

예시 C. 큰 포스터는 전체 이미지와 타일을 함께 처리하였다

  • 긴 변이 1,800픽셀을 넘으면 1,600픽셀 타일을 추가하였다. 타일 간 160픽셀을 겹쳤다.
  • 타일 OCR 좌표를 원본 위치로 되돌린 뒤, 겹치는 문자열을 병합하였다.
  • Paddle 보완 42개에서는 총 85개 뷰를 처리하였다. 원시 999줄이 병합 후 877줄이 되었다.
  • 확인한 문제: 줄 수는 늘어도 부분 문자열·중복·읽기 순서 때문에 제목과 날짜가 끊어질 수 있었다.
  • 수정 방향: 전체뷰 결과를 유지하고 타일 결과는 별도 관찰로 전달해야 한다.

3-4. 전체 실행과 자세한 내용 검토를 나누었다

모델이 결과를 반환하는지는 전체 299개에서 확인하였다. 다만 결과가 실제 이미지와 맞는지 자세히 비교하려면 유형별 검토가 필요했다. 그래서 사진·아이콘·로고 등 36개에 작거나 큰 이미지 6개를 더해 42개를 따로 살펴보았다. 42개는 새 데이터가 아니라 299개 중에서 고른 일부이다.

4. 공개 모델을 활용해 “한 장씩 넣고 결과를 모으는 실험 도구”를 만들었다

이번에 새 비전 모델을 학습시킨 것은 아니다. 공개된 모델을 로컬에서 실행할 수 있도록 준비하고, 같은 샘플을 각 모델에 넣어 결과를 파일로 저장하는 프로그램을 구성하였다. 한 이미지에서 나온 설명과 글자를 나란히 비교할 수 있게 한 것이다.

4-1. 프로그램은 한 이미지에 대해 이렇게 동작하였다

4-3. “이미지의 일부만 모아 설명하면 나아질까?”도 확인하였다

Patch-ioner의 영역 기능도 실제로 시험하였다. Florence가 이미지 안에서 설명할 영역을 찾게 한 뒤, 그 영역에 해당하는 패치 정보를 모아 Patch-ioner가 다시 설명하도록 연결하였다. 사람이 정답 영역을 지정한 실험은 아니며, 두 공개 모델을 연결한 추가 비교이다.

  • 공개 모델에 추가 학습은 하지 않았다.

5. 돌려 보니, 글자를 읽는 일과 장면을 설명하는 일은 결과가 달랐다

먼저 개별 이미지를 보고 모델 출력을 대조하였다. 아래에서는 대표적인 결과를 말로 설명한 뒤, 같은 경향을 확인하기 위해 정리한 수치를 붙였다. 수치가 높다고 곧바로 대회에서 좋은 점수가 나온다는 뜻은 아니다.

5-1. 로고와 안내문의 핵심 글자는 OCR가 더 직접적으로 읽었다

국립중앙도서관 로고를 넣었을 때, Patch-ioner는 “사람이 있는 표지판”처럼 설명하였다. 반면 OCR에는 “문화체육관광부”, “국립중앙도서관”이 남았다. 이런 이미지에서는 그림의 인상을 길게 설명하는 것보다 실제 글자를 읽는 단계가 필요함을 확인하였다.

이 차이를 조금 더 확인하려고 29개 이미지에서 기관명·날짜·전화번호 등 72개 문구를 골랐다. 각 모델의 출력에 그 문구가 남았는지 세어 보니 다음과 같았다. 57/72는 “선정한 72문구 중 57개가 출력에 있었다”는 뜻이며, 전체 OCR 정확도 79.2%라는 뜻은 아니다.

  • 합집합 수치는 어느 한 엔진에 해당 문구가 있었는지를 뜻한다. 시스템이 정답을 자동 선택했다는 의미는 아니다.
  • 채점 방식: 공백·문장부호를 제외하고 정규화한 문구가 출력 안에 연속해서 포함되는지 검사하였다.
  • 이 수치는 선택 문구 포함 여부이다. OCR 전체 정확도, CER, 최종 대회 F1로 해석하지 않았다.

5-2. Florence가 그림을 더 잘 잡은 사례도 있었지만, 그대로 믿을 수는 없었다

마이크를 들고 말하는 사진에서는 Patch-ioner가 마이크를 와인잔으로 설명했고, Florence는 마이크를 알아보았다. 악수 아이콘도 Florence는 악수로 설명하였다. 그래서 그림·사진의 내용을 보완할 비교 모델로 활용할 여지는 있었다.

그러나 국민연금 문구가 있는 홍보 이미지를 Florence가 “한국 드라마 홍보물”이라고 설명한 사례도 있었다. 사진의 큰 형태를 알아봐도 목적이나 상황을 지어낼 수 있었던 것이다. 핵심 36개를 이미지와 직접 대조한 기록은 아래와 같다.

  • Florence는 중심 대상을 더 자주 포착하였다. 그러나 보이지 않는 행동·목적과 잘못된 한글을 추가하였다.
  • Florence 상세 설명은 이 36개 중 19개에서 이미지와 다른 문자·문구를 생성한 것으로 점검하였다.

5-3. 부분을 골라 설명하게 해도 오류가 자동으로 해결되지는 않았다

마이크 사진의 전체 설명이 틀렸으므로, 이미지 일부에 집중하도록 패치를 모아 다시 설명하게 하였다. 출력은 달라졌지만 마이크가 이번에는 전화기로 바뀌었다. 로고에서는 기관명 대신 따옴표가 반복되었다. 즉, 보는 범위를 조절하는 기능과 한글을 읽는 능력은 다른 문제였다.

16×16 숫자 3은 확대 후 두 OCR에서 읽혔다. 반면 큰 포스터는 나눠 읽은 결과를 합치는 과정에서 제목이나 날짜가 끊어졌다. PP-OCRv5의 선택 문구 포함 수도 기본 57개에서 보완 후 56개로 줄었다. 따라서 보완 처리는 효과를 확인하면서 적용하고, 원래 결과도 함께 보관해야 한다고 판단하였다.

5-5. 여기까지 확인한 범위

  • 최종 통합 결과에서는 기본 3개 구성요소가 각각 299개를 처리하였다. 빈 문자열 반환도 기술적 성공에 포함하였다.
  • 실행이 끝났다는 이유로 한국어·숫자·객체 설명을 정답 처리하지 않았다.
  • 원문과 오류를 그대로 남겨 다음 단계에서 다시 확인할 수 있게 하였다.

6. 실제 이미지를 보면 위 결과를 더 쉽게 이해할 수 있다

예시는 “이미지에 실제로 무엇이 있는가 → 그림 설명 모델은 무엇이라고 했는가 → OCR에는 어떤 글자가 남았는가” 순서로 보면 된다. 잘된 사례와 틀린 사례를 함께 넣었다. 아래 12개 외에 유형별 43개 예시와 299개 전체 결과도 별도 페이지에서 볼 수 있다.

  • 왼쪽에서 이미지를 보고, 오른쪽에서 확인 메모와 모델 원문을 함께 읽도록 구성하였다.
  • 영어 원문은 모델 출력이다. 오류를 자연스러운 문장으로 고쳐 쓰지 않았다.

7. 그래서 다음에는 “글자 + 그림 설명 + 웹 문맥”을 함께 넘기려 한다

지금 결과로는 어느 모델의 문장 하나를 이미지의 정답 설명으로 삼기 어렵다. 대신 OCR가 읽은 글자, 모델이 설명한 장면, 원래 페이지의 문맥을 따로 보관한 뒤 LLM이 함께 보도록 연결하는 구성을 제안하였다.

국립중앙도서관 로고라면 OCR가 읽은 기관명을 전달하고, 그림 설명 모델이 말한 “사람이 있다”는 주장은 미확인으로 남길 수 있다. 여기에 링크 여부와 주변 글을 추가하면, 기존 alt가 기관명이나 링크 목적을 충분히 설명하는지 판단하는 데 필요한 재료가 된다. 이는 다음 단계의 활용 예이며, Gemma가 실제로 판정한 결과는 아니다.

다음 단계에서 연결할 흐름

  1. 이미지 입력을 정리한다.방향·투명도·SVG·크기를 확인하고 원본을 보존한다.
  2. 한국어 글자와 장면을 각각 추출한다.PP-OCRv5 원문·좌표와 Florence 시각 설명 후보를 분리한다.
  3. 필요한 입력만 다시 관찰한다.작은 글자·낮은 대비·긴 포스터에 확대·대비·타일을 비교한다.
  4. 출처와 충돌을 남긴다.전체뷰와 보완뷰를 함께 저장하고, 어느 결과에서 나온 주장인지 표시한다.
  5. 메타데이터를 붙여 LLM으로 전달한다.기존 alt·링크·주변 문맥을 추가하고 최종 품질 판정에 사용한다.
이번에 만든 것다음에 구현·검증할 것
299개 이미지의 OCR·caption 후보와 문맥을 분리한 JSONGemma 12B-QAT의 최종 7범주 판정
정답 label·참조 문구·시각 점검 판정을 제외한 LLM 입력 묶음OCR만 / caption만 / 둘 다 넣는 비교 실험
기본 결과·보완 결과·오류 기록필요한 사례만 재관찰하는 자동 분기
실행 환경과 단일 이미지 재실행 진입점문서 구조 모델·사실 확인 모듈 추가 비교
  • 고유명사·날짜·숫자: caption에서 추정하지 않고 OCR 원문과 box를 우선 증거로 사용한다.
  • 국적·신분·행사 목적: caption이 말하더라도 픽셀 근거가 부족하면 미확인으로 남긴다.
  • 메타데이터: 최종 판정에서 기존 alt·문맥은 사용할 수 있다. 정답 label과 라벨러 설명은 제외한다.
  • Gemma: 이 PC에서는 비전 결과 저장 → 비전 모델 해제 → LLM 순차 실행을 우선 검토한다. 아직 속도와 분류 성능을 측정하지 않았다.
  • 웹 확인: 링크 목적·주변 설명처럼 부족한 문맥을 선택적으로 보완하는 용도로 제안한다. 대회에서 참가 시스템의 외부 인터넷 이용이 허용되는지는 별도 확인이 필요하다.
